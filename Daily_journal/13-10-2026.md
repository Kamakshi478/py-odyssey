# Test Driven Development 
  - Test-Driven Development (TDD) is a software engineering practice where you write automated unit tests before you write the actual application code.
  - It is a design methodology that flips traditional programming on its head: instead of writing code and then testing it to see if it works, you use tests to define and drive the behavior of how your code should be built.

## The Three Golden rules of TDD 
Uncle Bob (Robert C. Martin), a pioneer of agile software development, defined TDD through three strict rules:
  - You are not allowed to write any production code unless it is to make a failing unit test pass.
  - You are not allowed to write any more of a unit test than is sufficient to fail (and not compiling/running is a failure).
  - You are not allowed to write any more production code than is sufficient to pass the one failing unit test.

## The Core Concept: The "Red-Green-Refactor" Cycle
TDD relies entirely on a rapid, repeating loop:
  - 🔴 Red: Write a tiny, automated test for a feature that does not exist yet. Run the test and watch it fail
  - 🟢 Green: Write the bare minimum, simplest production code required to make that specific test pass.
  - 🔵 Refactor: Clean up the code you just wrote (remove duplication, improve naming, optimize structure) while ensuring the test stays green.

### 🔴 Red (Write a failing test)
Before you write a single line of business logic, you write a unit test that verifies the feature exists and works correctly.
  - Why it fails: Since the actual code doesn't exist yet, running this test must fail (or result in an error).
  - The Benefit: This proves that your test is actually capable of catching a failure. If you write a test and it passes immediately, your test is flawed.
### 🟢 Green (Write code to pass)
Your sole objective in this step is to write the absolute minimum amount of code required to make that failing test turn green (pass).
  - • Don't over-engineer: You are allowed to write "ugly" or hardcoded code here. Do not try to predict future features or write elegant architecture. Just solve the immediate problem.
### 🔵 Refactor (Clean up)
Now that your code passes the test, look at what you just wrote.
  - The Goal: Clean up the code. Remove duplication, improve variable naming, split large functions into smaller ones, and make it readable.
  - The Safety Net: Because you have a green test, you can change the internal structure of your code with total confidence. If your refactoring breaks something, the test instantly turns red again.
